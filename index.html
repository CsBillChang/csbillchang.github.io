ResearchLoop 科研情报与证据研读 Agent 平台 github.com/CsBillChang/ReasearchLoop

架构设计 / 后端研发

项目描述：面向持续文献跟踪与课题调研，设计并实现多智能体科研应用，通过自然语言完成需求澄清、论文发现、原文研读、跨篇比较与笔记整理，结合用户研究画像生成增量论文简报，提供可追溯的证据与研究成果。

技术栈：Python / FastAPI / LangGraph / MySQL / Qdrant / BM25 / RRF / Cross-encoder / PyTorch / SSE

一、多 Agent 工作流与架构设计

  • ReAct＋Reflection＋Memory：构建“任务分析—工具执行—观察反馈”的自主研究循环，根据研究目标与执行结果动态选择检索、研读和证据查询；通过 Reflection 补读原文、核查事实矛盾与信息缺口，结合 Memory 中的研究历史和用户偏好支撑多轮任务决策。
  • 多 Agent 协作架构：基于 LangGraph 编排 Supervisor—Researcher—Reviewer，分别承担规划汇合、并行取证与独立审校，配置角色独立上下文和工具白名单，通过结构化子任务传递目标、材料范围与研究发现；采用共享规则、角色职责与按需任务模式的可组合设计，统一目标解释、成果复用和交接约定，使可用任务平均端到端执行耗时降低 31.99%，平均单任务总 Token 减少 42.61%。
  • 反馈驱动路由：根据任务覆盖和工具观察选择补证、审校或交付，区分支持、反证与缺证；将审校绑定当前稿件及来源版本，隔离历史批评，通过精确局部修改保留非目标内容，根据补充证据、修订进展和未解决项决定继续或结束。

二、工具集成与证据检索

  • 科研工具体系：统一接入论文搜索、全文读取、证据查询、精读总结和成果保存，通过结构化参数、角色权限及材料 ID、版本校验控制执行；针对来源限流、获取失败和解析异常执行退避、路径回退与缺口报告，保留工具结果及来源身份。
  • 版本化 RAG 与检索优化：按段落与 Token 边界切分论文，保留章节、页码、版本和字符偏移，支持 BM25＋Qdrant 双路召回及 RRF 融合；默认采用标题／章节定位、概念扩展和 BM25 候选筛选，通过 Cross-encoder 联合编码查询与候选片段，进行相关性评分与二次排序，使 Recall@10 由 59.82% 提升至 78.13%、MRR@24 由 0.2703 提升至 0.5400，热查询 P50／P95 耗时为 631.52／757.23 ms；通过任务授权过滤和原文读回定位回答依据。

三、研究状态与分层记忆

  • 共享研究状态（AgentState）：统一维护研究目标、用户约束、子任务结果、证据和稿件身份，结合 MySQL 持久化任务进展，为跨 Agent 成果复用、材料交接、澄清恢复和后续执行提供统一依据。
  • 分层 Memory：分离会话上下文、研究历史和长期画像，支持相关历史召回、自然语言偏好录入与可撤销兴趣推断；将已答澄清及来源身份纳入历史索引，支持跨会话研究条件读回，对显式偏好执行用户原文来源与逐字摘录校验；明确当前指令、显式偏好和推断兴趣的优先级，减少临时要求混入长期画像，历史记忆不继承文件写入授权。
  • 上下文管理与个性化追踪：采用抽取式压缩和可追溯归档管理历史消息，保留目标、约束与产物身份，通过工具按需读回原始记录；结合研究方向、已读与曝光历史生成每日论文简报，支持论文版本去重及停机后的合并补报。

四、持久执行与故障恢复

  • 任务执行可靠性：基于 MySQL 原子领取、Worker 租约和自实现执行快照管理任务生命周期，模型响应与用量先持久化再解析，恢复时复用成功收据，对未知请求阻断盲目重发；成果保存采用版本校验、内容 hash 与幂等控制，保护已有文件并处理重复执行。
  • SSE 流式交互：基于 FastAPI 与独立 Worker 解耦任务执行和页面连接，通过 SSE 推送工具进度与回答增量，利用事件序号和 Last-Event-ID 实现断线补发，支持澄清后接续与任务取消，并验证并发领取、进程中断恢复和重复保存等边界。

惠享生活 · Go 本地生活服务平台 github.com/CsBillChang/EnjoyLife-Platform

后端核心开发

项目描述：面向本地商户与消费者，设计并实现店铺与活动查询、优惠券抢购、模拟支付、核销及退款，处理热点访问、库存竞争和履约冲突。

技术栈：Go / Gin / GORM / MySQL / Redis / RabbitMQ / Ristretto / Docker Compose / pprof

一、缓存架构与查询优化

  • 多级缓存与热点回源：构建 Ristretto＋Redis 两级缓存，通过 singleflight 合并回源；店铺采用空值缓存、随机/逻辑过期与有界刷新，活动采用固定 TTL、详情负缓存与列表版本隔离，将店铺详情查询 P95 由 33.427 ms 降至 5.179 ms，降低 84.51%。
  • 缓存一致性与交易隔离：将业务更新与失效任务同事务提交，通过租约重试清除当前实例 L1 与共享 Redis L2，以 TTL 兜底；下单重读 MySQL 活动状态、价格与库存，避免陈旧展示影响成交。

二、抢购链路与异步成单

  • Lua 准入与库存控制：通过 Redis Lua 原子校验时段、处理截止、资格与限购并预占；MySQL 事务内结合条件扣库存、用户与活动组合唯一约束和库存流水，处理重复成单与幂等回补，以代际校验隔离重建后的旧请求与补偿。
  • 事务消息与故障恢复：将准入状态与 Outbox 同事务保存，通过 RabbitMQ 发布确认、提交后 Ack 和幂等消费实现异步成单；结合持久请求、终态查询与扫描恢复中断，验证提交后未 Ack 的重投。

三、交易履约与性能治理

  • 支付、核销与退款：通过条件状态流转处理重复回调、支付与关单竞争、迟到支付补偿及退款与核销冲突；结合商户归属、券状态和唯一回补记录控制副作用，支持支付、核销记录的权限过滤与游标分页。
  • 并发控制与分配优化：使用 Redis Lua 按活动和用户限流，结合 Prefetch、有界 Worker 与 context 管理消费并发、超时和退出；通过 pprof 分析锁等待与分配，将店铺详情响应由 map 改为结构体，使 handler 微基准由 25 降至 20 allocs/op，分配次数减少 20%。
